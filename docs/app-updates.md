# App update implementation and verification

The previous app had network-first PWA navigation and immutable frontend assets, but no server update discovery or installation. The new managed entrypoint adds both. See [update usage](guide.md#updates).

## Reference and choices

Inspected `devswha/chatmux` at commit `3b1f3b49216157399e3fb9666a49c942908c3e32` in `/home/devswha/workspace/chatmux`. Its [version check hook](https://github.com/devswha/chatmux/blob/3b1f3b49216157399e3fb9666a49c942908c3e32/src/hooks/useVersionCheck.ts) periodically checks for updates; its [self-update service](https://github.com/devswha/chatmux/blob/3b1f3b49216157399e3fb9666a49c942908c3e32/server/self-update.ts) handles source/release installation. Chatmux is AGPL-3.0; herdr-web-ui is MIT. This implementation adopts behavior and contains no copied chatmux code.

| Priority | Adopted behavior | Implementation |
| --- | --- | --- |
| 1 | Automatic discovery, explicit install | Supervisor checks after 10 seconds/every 5 minutes for the highest plain `vX.Y.Z` tag (bundle `remote-v*` tags and pre-releases are ignored; annotated tags are peeled to their commit); Settings provides check/install controls |
| 2 | Protect locally modified or diverged source | Clean `main` checkout required (herdr's shallow, detached plugin checkout is accepted when running as that plugin); exact target SHA and ancestry verified; source worktree never rewritten |
| 3 | Verify deployment and recover | Build isolated checkout, restart bridge, match a fresh boot ID through health, restore prior build on failure |
| 4 | Optional unattended installation | `OVIS_AUTO_UPDATE=1`; persist failed SHA to prevent repeating a bad automatic deployment |

Chatmux's systemd-specific launcher and release archive pipeline were not adopted: this repository distributes Git source through Bun and herdr plugins, including macOS. The supervisor uses [Bun's supported IPC](https://bun.sh/docs/runtime/child-process#inter-process-communication-ipc). No runtime dependencies were added.

## Boundaries

- `server/managed.ts` is the launcher: the process `bun run start` and the plugin start and record. It runs `server/supervisor.ts` from the active release (`current.json`, only while it matches the source checkout's HEAD), else its own copy. `server/supervisor.ts` owns the bridge process and health-checked rollback. `server/updater.ts` owns bounded Git/build commands, source guards, release selection and persistence. Only the supervisor runs discovery timers.
- Supervisor handover: after an install passes the bridge health check and is committed, the supervisor exits with 75 before reporting `idle`; the launcher then starts the new release's supervisor, which restarts the bridge from the same release (a second brief reconnect). A new supervisor that exits before it reports ready is replaced by the previous one (then the checkout's own), which runs the new release and reports the failure in the update status until the next update. Handover only happens under the launcher.
- `server/update-api.ts` relays requests/status over IPC. `/api/updates*` uses the existing token gate; POSTs require a custom header and reject cross-site browser requests. The browser cannot choose an executable, directory, remote or revision: an install names the offered release, sending its `latest_revision` as `expected_revision` (`POST /api/updates/install`, a JSON body of at most 1 KiB), and the bridge refuses one that names none (400 `invalid_update_install`) or another release (409 `update_offer_changed`). The bridge forwards it over IPC as `update-install-revision`, a message an older supervisor does not know and so ignores, and accepts installs only while the supervisor's status carries `revision_bound_install: true` (else 409 `update_restart_required`, and the controls ask for a restart instead of offering an install). The supervisor ignores an unbound `install` from an older bridge, and installs only while the check the install starts with still offers that revision: a release published in between installs nothing and ends in `error_code: "update_offer_changed"`. `GET /api/updates/notes` answers what the offered release brings: the supervisor reads the `CHANGELOG.md` of the release's own commit (`git show <revision>:CHANGELOG.md`, fetched with its tag, no other network call) and `server/release-notes.ts` keeps the sections after the running version, up to the release, newest first and bounded in size. The notes travel beside the status over IPC and stay out of `GET /api/updates`, which is polled. A release without a readable changelog section is offered without notes. A release also tells itself as patch notes in `release-summaries.json`: short lines per UI language under what is new, improved and fixed (`{ "X.Y.Z": { "en": { "new": [], "improved": [], "fixed": [] }, "ko": …, "ja": …, "zh": … } }`), read from the same commit and sent with its section as `summary`; a release that wrote none is told by its section alone. `GET /api/updates/installed` answers what the last update brought once the new release runs: the supervisor reads the running release's own `CHANGELOG.md` and `release-summaries.json` from disk, from the version it replaced. The installing supervisor writes that version and the time into `current.json` (`previous_version`, `installed_at`). A supervisor older than that record leaves none, and then the version is the newest older build still present (an install keeps the release it replaces, and the source checkout stays) and the time is the record's own. A source checkout that no update installed answers, for its commit, that there is none; an answer that names no commit is a supervisor that has not told yet, and the client asks again a few times.
- `shared/update.ts` defines the status contract. `src/lib/updates.ts` polls it after authentication. `UpdateControls.tsx` displays Settings controls, the release's notes (fetched once per offer and kept only when read from the offered commit, `src/lib/updateNotes.ts`) and the header notice, whose **Update** button installs the release from there. After the reload the notice tells of the update for a week, until the device closes it or opens its notes (`announcesUpdate`, a version kept in `localStorage`), and Settings keeps what the last update brought. A release with a summary shows its lines in the app's language (English when that language is missing) under **New features**, **Improvements** and **Bug fixes**, with its changelog section folded under them. While a newer release is known, the notice is that release's, and Settings shows both sets of notes. Both both show the install's `step` (download, dependencies, typecheck, build, restart) as a step count and a bar. The compiled frontend revision identifies when a reload is needed; reloading remains explicit to preserve drafts.
- A source checkout that is replaced under the running server (plugin reinstall, or `git pull` and a build) is served from its new files while the server keeps reporting the revision it started with, so reloading the tab loads the same build again. Each client build writes the commit it was made from to `dist/build.json` (`vite.config.ts`). `GET /api/updates` adds it as `served_revision` once it differs from `current_revision` (null while they match, or for a build older than the file). The bridge reads it itself (`servedRevision` in `server/update-api.ts`), from the `dist/` of the directory the supervisor started it in, each time a tab asks: no timer, and no wait for the supervisor's 5-minute check. It is the build a reload loads, not the checkout's HEAD, so a checkout moved without a build is not mistaken for one, and only a build written after the bridge started counts: a pull without a build followed by a restart leaves an older build that a restart cannot change. The file names a commit, so a rebuild with uncommitted changes looks like the build before it. When it equals the tab's own revision, `reloadReason` returns `"restart"`: the notice and the Settings status line ask to restart the app on the PC, with a link to the restart commands, in place of **Reload app**. In Settings the line takes the place of the check's own `CHECKOUT_CHANGED_REASON`; any other blocker stays under it. A part of the page that failed to load keeps its reload (`"incomplete"`) first. The line ends when the restarted server reports that revision.
- `bun run start` and plugin `start` use the supervisor; `bun run server` remains unmanaged. Restart an older running server once to adopt this entrypoint. Updates replace the supervisor through the handover above; only the launcher (`server/managed.ts`, kept small and dependency-light) stays loaded from the source checkout, so a launcher change needs a restart from an updated checkout (plugin reinstall or `git pull`).
- Update data is separate from push keys/subscriptions. State and socket paths are resolved before launching a candidate, so changing the candidate working directory cannot redirect either. The source checkout and the two most recent successful isolated builds remain available.
- Discovery/build failures keep the serving bridge alive. A failed candidate boot restores the previous build. If both candidate and previous build cannot start (for example herdr is unavailable), the failure remains in supervisor logs and needs normal service recovery.

- `bun run typecheck` and `bun run build` passed.
- `bun scripts/update-browser-qa.ts`: actual source copy, private Git remote, candidate dependency installation/typecheck/build, the release's summary and folded notes in Settings and from the header line's **What's new**, desktop check/install, new frontend reload, the line that tells of the update and what it brought, retained unsent draft and owned herdr pane, deliberately failed server boot/rollback, mobile update-section bounds, and no browser JavaScript errors. The temporary server, browser and workspace are cleaned up.
